Overview

The Agent2Agent (A2A) Protocol is an open standard for communication and collaboration between AI agents. Originally developed by Google and donated to the Linux Foundation, A2A provides a common language for agent interoperability in environments where agents are built using diverse frameworks (LangGraph, CrewAI, ADK, Semantic Kernel, custom in-house stacks) and operated by different vendors or teams. [1]

A2A is intentionally complementary to MCP rather than competitive: a typical production agent equips itself with tools via MCP and communicates with other agents via A2A. The protocol uses HTTP plus JSON-RPC and is designed so that an agent’s internal logic — its memory, tools, and reasoning loop — stays opaque to the client. [1]

Core Concepts

Actors: Client and Server

A2A defines two roles in any interaction:

  • A2A Client (Client Agent): An application, service, or another AI agent that acts on behalf of a user. The client initiates communication.
  • A2A Server (Remote Agent): An agent or agentic system that exposes an HTTP endpoint implementing A2A. From the client’s perspective the remote agent is a black box; only its A2A surface is visible. [2]

Any agent can play either role, and many real systems both serve and consume A2A.

Agent Card

The Agent Card is a JSON metadata document that acts as the “business card” of an A2A agent. It declares the agent’s identity, capabilities, endpoint URL, authentication requirements, and the list of skills it offers. Clients fetch this document during discovery to decide whether and how to interact with the agent. [2]

Skills

Each agent exposes a list of named skills with descriptions, input/output schemas, and metadata. Skills are the unit of capability advertised in an Agent Card and the unit of invocation in a task. [3]

Task

A Task is a stateful unit of work initiated by a client and processed by a server. Tasks have unique IDs, defined lifecycles, and support long-running multi-turn operations. The “Life of a Task” concept covers task creation, status transitions, intermediate messages, and final artifacts. [2]

Message and Part

A Message is a single turn of communication, carrying a role (user or agent) and a unique messageId. Messages contain one or more Parts:

  • Text part: plain text content
  • File part: a file reference (URL or inline bytes)
  • Data part: structured data (JSON) [2]

Parts give agents a flexible content envelope for mixing prose, structured outputs, and file attachments in either direction.

Artifact

An Artifact is a tangible output generated by an agent during a task — for example, a generated document, an image, or a structured-data payload. Artifacts are returned as part of task progress and represent the agent’s concrete deliverables, distinct from the chat-style Message stream. [2]

Agent Response: Task or Message

An A2A server can respond to a request with either a Task (when it accepts a stateful unit of work) or a Message (when a simple single-turn response is enough). This dual mode lets the same protocol serve both quick Q&A interactions and long-running collaborations. [2]

Architecture

A typical A2A exchange:

  1. Discovery: Client fetches the server’s Agent Card (often at a well-known URL like /.well-known/agent.json) to learn capabilities, endpoint, and auth requirements.
  2. Request: Client sends a request over HTTP+JSON-RPC, specifying a skill and message content. Auth is enforced per the Agent Card’s declared scheme.
  3. Task creation: Server accepts the request as either a one-shot Message response or a stateful Task.
  4. Progress: For tasks, the server streams updates via Server-Sent Events (SSE), pushes notifications to a client webhook, or makes status available for polling depending on the interaction mechanism agreed.
  5. Artifacts: When the task completes, the server returns one or more artifacts plus a final status. [2]

Interaction Mechanisms

A2A supports three patterns for delivering results, chosen per-skill or per-call:

  • Request/Response: Client sends a request and the server responds inline; for long-running tasks, the client polls the server for status.
  • Streaming via SSE: Client initiates a stream and receives incremental status and intermediate messages over an open HTTP connection.
  • Push Notifications: For very long-running or disconnected scenarios, the server sends asynchronous notifications to a client-provided webhook when task updates occur. [2]

Key Features and Functionality

Cross-Framework Interoperability

A2A is framework-agnostic: an agent built in Google ADK can call an agent built in LangGraph, CrewAI, or a hand-rolled Python service as long as both speak A2A. This decouples agent composition from any single framework’s runtime. [1]

Opaque Remote Agents

Servers are deliberately black-boxed. A client does not see the remote agent’s internal tools, memory, or model choice — only its declared skills and the messages/artifacts it returns. This separation makes A2A suitable for multi-organization and multi-vendor agent networks. [2]

Enterprise Features

The protocol includes provisions for authentication (per the Agent Card’s declared scheme — typically OAuth or API key), authorization, observability hooks, and extension points for organization-specific requirements. [4]

Extensions and Custom Bindings

A2A supports extensions for adding optional capabilities and custom protocol bindings for transports beyond HTTP+JSON-RPC. Governance for extensions and bindings is documented separately to keep the core protocol small. [5]

Streaming and Multiturn

Multi-turn interactions are first-class: a Task can continue across many messages, with both sides exchanging content until the task reaches a terminal state. Streaming over SSE delivers incremental output to the client as the server generates it. [6]

Use Cases

Multi-Agent Workflows

A coordinator agent decomposes a high-level goal into sub-tasks and delegates each to a specialized remote agent over A2A — a research agent, a coding agent, a data-analysis agent — and assembles their artifacts into a final answer.

Vendor-to-Vendor Agent Integration

An enterprise’s internal procurement agent calls a vendor’s hosted A2A agent to negotiate or request information. Both sides keep their stacks opaque; only Agent Cards, skills, and messages are exposed.

Human-in-the-Loop Workflows

A long-running task surfaces status to the client; the client pauses for human approval before letting the remote agent proceed to the next phase, using the Task lifecycle to track approval state.

Agent Marketplaces

A registry of Agent Cards lets developers discover and integrate third-party agents the way they’d integrate APIs — but with richer capability descriptions and standard interaction patterns.

SDKs

The Python SDK is the canonical reference implementation, with examples covering Agent Skills + Agent Card, Agent Executor, server startup, client interaction, and streaming/multiturn flows. SDKs for other languages are in progress in the community. [7]

Configuration

Agent Card Hosting

By convention, an A2A server publishes its Agent Card at a well-known URL on its endpoint host. The JSON document declares:

  • Agent identity (name, description, version)
  • Service endpoint URL
  • Supported A2A capabilities (streaming, push notifications, extensions)
  • Authentication requirements
  • List of skills with input/output schemas

Authentication

Authentication is declared in the Agent Card and enforced at the HTTP layer. The protocol does not prescribe a single auth method — OAuth, API keys, mTLS, and custom schemes are all permitted via the Agent Card’s authentication field. [4]

Integration Patterns

With MCP

The two protocols are complementary: agents equip themselves with tools and data sources via MCP, and communicate with other agents over A2A. A typical agent’s outer surface is A2A; its inner surface (to tools and data) is MCP. [1]

With Agent Frameworks

Agent frameworks (LangGraph, CrewAI, ADK, Semantic Kernel) can wrap A2A as both a transport for outgoing calls (treating remote A2A agents as remote tools) and as a server interface for exposing their own agents to other systems.

With API Gateways

Because A2A is HTTP+JSON-RPC at the transport layer, standard API gateways, observability stacks, and rate-limiting infrastructure work without protocol-specific adapters.

Examples

Minimal Python Server

from a2a.server import AgentServer
from a2a.types import AgentCard, Skill

card = AgentCard(
    name="echo-agent",
    description="Echoes the user's message back",
    endpoint="https://example.com/a2a",
    skills=[Skill(name="echo", description="Echo input")],
)

async def echo_executor(task):
    text = task.message.parts[0].text
    yield {"role": "agent", "parts": [{"type": "text", "text": text}]}

server = AgentServer(card=card, executor=echo_executor)
server.run(port=8000)

Minimal Python Client

from a2a.client import A2AClient

client = A2AClient.from_url("https://example.com/a2a")
response = await client.send_message(
    skill="echo",
    parts=[{"type": "text", "text": "hello"}],
)
print(response.message.parts[0].text)

(Shapes are illustrative; consult the Python SDK reference for the exact API.) [7]

Limitations and Considerations

  • Young protocol: v1.0 is stable but the surrounding ecosystem (gateways, registries, framework integrations) is still maturing.
  • Opacity is a feature, not a bug: clients cannot inspect the remote agent’s internal reasoning. Logging and tracing must be designed end-to-end across both sides.
  • Auth heterogeneity: Each Agent Card can declare a different auth scheme. Clients that consume many remote agents need to handle multiple schemes uniformly.
  • Long-running tasks: Push notifications require the client to host a webhook; in environments where that’s infeasible, fall back to polling or streaming.
  • Discovery is not centralized by default: Each agent publishes its own Agent Card; registries are a layer above the protocol.

Specification

The canonical specification lives at a2a-protocol.org/latest/specification/, with a separate “What’s New in v1.0” document for migration notes. The protocol is governed under the Linux Foundation. [8]

Problem Statements

  • Agents built in different frameworks cannot natively talk to each other
  • No standard way to advertise an agent’s capabilities or auth requirements
  • Long-running agent tasks require ad-hoc polling or webhook plumbing
  • Multi-vendor agent networks need a black-box interaction model
  • Each remote agent may declare a different auth scheme
  • Discovery is decentralized; registries are a layer above the protocol
  • Logging and tracing must be designed end-to-end across opaque peers

When to Pick This

  • Pick A2A when your problem is agent-to-agent delegation across frameworks or vendors (not agent-to-tool — that is MCP)
  • Pick A2A when remote agents should remain opaque black boxes — only Agent Cards and skills visible
  • Pick A2A when you need long-running, multi-turn tasks with streaming or push notifications
  • Pick A2A when building an agent marketplace or registry of third-party agents
  • Pick A2A alongside MCP: A2A is the agent’s outer surface, MCP is its inner (tool) surface
  • Pick MCP instead when the integration is between an agent and a tool/data source within your own stack
